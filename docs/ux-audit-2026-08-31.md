# UX Audit and Serial Fix Queue

Date: 2026-08-31
Scope: public landing surface, public event guest surface, RSVP flow, host workspace, and host guest preview.

## Review protocol

Reviewed the live product and source implementation at:

- public landing route (`/`)
- sample guest event route (`/demo`)
- sample host workspace route (`/demo/host`)
- light and dark themes
- desktop viewport: 1440x900
- mobile viewport: 390x844
- narrow mobile viewport: 320x700

Also checked responsive overflow, mobile navigation, in-page navigation after smooth-scroll settles, form control semantics, and rendered theme color tokens.

## Findings

### P1 — Light-theme accent text contrast

Light-theme primary orange text is approximately `#d97706` on `#f5f5f4`, measured at about 2.92:1. It is used for normal-size schedule labels, times, and key-event text. Dark-theme primary contrast passes at approximately 6.20:1.

Acceptance:

- light-theme normal-size accent text meets WCAG AA contrast;
- dark-theme appearance remains intentional;
- buttons retain readable text and focus states;
- no unrelated color roles are changed.

### P1 — Primary RSVP task is buried

On a 390px viewport the RSVP section begins around pixel 4385 of a 6244px sample page. The first viewport contains no RSVP call to action. The page has an RSVP navigation link and a later action-item link, but the primary guest task is not surfaced immediately.

Acceptance:

- a guest can discover and reach RSVP from the first screen;
- the hero remains calm and event-focused;
- mobile and desktop navigation still work;
- long-page anchor behavior remains correct.

### P1 — New RSVP forms default to affirmative attendance

The live sample displays Yes selected. The form default helper also initializes a new form's attendance status to `attending`.

Acceptance:

- a new guest must explicitly choose Yes, Maybe, or No;
- existing saved RSVPs still prefill their stored choice;
- validation and update behavior remain intact.

### P1 — Sample/demo disclosure arrives too late

The sample page presents a realistic event at the top, while the non-persistent demo warning appears only near the RSVP form. The primary page content is not clearly labeled as sample content on first view.

Acceptance:

- sample mode is obvious before a user invests in the page;
- real event pages do not receive sample-only copy;
- disclosure works in both themes and on mobile.

### P1 — Header date range conflicts with itinerary

The sample header spans Friday through Monday, while the rendered itinerary ends Sunday with Head home and Departures. There is no Monday schedule entry explaining checkout or travel.

Acceptance:

- the displayed date range and schedule agree;
- departure-day semantics are explicit;
- date formatting remains correct across themes and viewports.

### P2 — Action items contain dead-end actions

The public action list says Book your flight and Settle up when the split lands, but those rows have no destination, control, or completion state. Only some action rows expose a CTA.

Acceptance:

- every imperative action either has a useful action/link or is reworded as information;
- action-item layout remains coherent with and without links;
- no fake or unsafe external destinations are introduced.

### P2 — Key-event treatment is unexplained

Guest schedule entries render an inline Key prefix, producing text such as Key Check in at the lodge. The public page does not explain the marker or provide a legend.

Acceptance:

- key events are understandable without editor knowledge;
- the treatment is visually distinct without relying only on color;
- screen-reader output is clear;
- host/editor key-event controls remain understandable.

### P2 — Flight optionality and driving path are ambiguous

The RSVP copy says Leave blank if driving, but it is not explicit that this applies to all arrival and departure fields. None of the four flight controls is individually marked optional.

Acceptance:

- driving guests understand what to leave blank;
- flying guests understand which fields are useful;
- the fields remain usable on narrow mobile screens;
- existing stored flight data is preserved when editing.

### P2 — Required RSVP fields are not identified in advance

On real event forms, Name and Attendance are required, but the guest-facing form provides no required marker or concise explanation before submission.

Acceptance:

- required fields are identified before submission;
- invalid submission gives focused, understandable feedback;
- sample mode remains non-submitting and clearly disabled.

### P2 — Public information grouping is inconsistent

The public guest experience uses several incompatible grouping grammars:

- **At a glance:** four facts are plain text with no card, grid, or divider boundary. On mobile they read as one text stream.
- **Do your part:** numbered rows rely mainly on whitespace; rows have no repeated boundary or completion treatment.
- **Activities:** the locked-in activity uses a card, while If time allows and Backups use mostly unboxed rows separated by subtle rules.
- **Pack:** checklist rows have no separators or surface grouping.
- **RSVP:** major form groups use subtle top rules but read as one long form; the Who is coming area uses a different card grammar.
- **Lodge:** the bordered statistics grid is clearer than the surrounding sections, but its grouping language is not reused elsewhere.
- **Host review:** confirmed facts use clear bordered mini-cards; this is a useful reference pattern, but the guest surface does not carry the same clarity.
- **Landing/create:** event-type controls are grouped reasonably, but the form hierarchy is stronger than the public event information hierarchy.

Acceptance:

- page sections, grouped components, and individual items have distinct, reusable grouping signals;
- not every block is converted into a card;
- borders, surfaces, dividers, spacing, and label hierarchy use consistent tokens in both themes;
- all public sections remain scannable at desktop, 390px, and 320px widths;
- host review/editor grouping is not regressed.

### P2 — Public page scan density is low

The sample guest page is 6244px tall at 390px width. Hero, summary, actions, and section spacing create large low-information gaps. This is separate from the grouping issue: even clearly grouped content can be more compact.

Acceptance:

- first-screen hierarchy improves without removing required logistics;
- section rhythm is consistent;
- sticky header and anchor targets retain safe offsets;
- no mobile content is clipped or horizontally scrollable.

### P3 — Theme toggle is icon-only

The light/dark control exposes an accessible label and title, but gives no visible text cue. This is a discoverability nit rather than a functional failure.

Acceptance:

- control remains compact on mobile;
- accessible name, pressed/state semantics, and persistence remain correct;
- the icon is legible in both themes.

## Verified non-findings

- No horizontal overflow was found at 320px.
- Mobile menu labels fit and remain tappable.
- In-page links reach their targets after smooth-scroll settles.
- Dark-theme muted and primary text samples pass contrast checks.
- Light-theme muted body text passed contrast checks; the material light-theme issue is the orange accent role.

## Serial release queue

Each queue item is intentionally a separate commit and release gate. The grouping audit itself is this commit.

1. Sitewide information grouping and boundary system.
2. Light-theme accent contrast.
3. RSVP first-screen discoverability and CTA path.
4. Explicit attendance choice for new RSVPs.
5. Sample/demo disclosure.
6. Itinerary/date-range consistency.
7. Action-item affordances and copy.
8. Key-event presentation.
9. Flight optionality and driving guidance.
10. Required RSVP field guidance.
11. Long-page spacing and scan density.
12. Re-audit all surfaces and add any newly discovered issues to the end of this queue.

## Per-commit release gate

For every implementation commit:

1. start the actual local app from the current `main` checkout;
2. verify light and dark themes at 1440x900 and 390x844;
3. verify narrow mobile behavior at 320x700 where relevant;
4. run focused tests, full tests, lint, typecheck, and production build;
5. run the repository pre-commit hook;
6. commit only the scoped change;
7. push the commit to `origin/main`;
8. read back remote `main`, GitHub checks, and deployment identity;
9. visually verify the exact deployed change in production at desktop and mobile in both themes;
10. stop and record the exact blocker after bounded retries if any gate fails.
